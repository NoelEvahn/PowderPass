Website Brief

How to plan, design, build, edit and prove a professional website: calm editorial clarity, purposeful spatial motion and an editor anyone can use. For any designer, developer or AI.

Starting point: Website Design Research: Editorial clarity, spatial motion, purposeful products (22 October 2026), five live references, observed and proposed. Proven on: a complete 31-page website and content editor built and reviewed in one project, with every motion value measured, tested and corrected by the site owner. 01 / How to use this brief

Order of authority. (1) The client's words in the current request. (2) The client's brand system and approved facts. (3) This brief. (4) The builder's own taste. When two instructions conflict, name the conflict and ask which wins. Never pick one silently.

Fits: any site that has to explain something real (an organisation, a product range, a service, a school, a studio) and still feel memorable. Does not fit: pure web apps, dashboards or long documentation, which need utility over atmosphere.

Deliver with every build: a responsive implementation; design tokens in one file; a component map; a motion trigger table (effect, trigger, values, fallback); a content editor with drafts, preview, roles and versions; database migrations; an editor guide; a sources register for facts and images; disclosure of anything unfinished, placeholder or unverified; and evidence for every item in chapter 16.

Never invent facts. Names, numbers, prices, dates, results, awards and claims come only from client-supplied sources. Anything awaiting confirmation is labelled in the content and listed in the sources register. Use the client's real photographs. Stock or generated images are used only when the client approves them, and are labelled as such.

How to read the status words

Each rule carries a status. Rule means it must be followed, Default means start here and change it with a reason, Avoid means it was tried and rejected, and Check means verify it before launch. In chapter 02, Keep, Changed, Dropped and New mark what happened to each research idea once it was built.

03 / Principles

Ten principles

1
Understand before spectacle. A calm grid, clear words and real photographs carry the information. Motion adds meaning or atmosphere and is never the only route to content.
2
Few signatures, well made. At most one signature scene per page (a spatial gallery, a sideways chapter or a lit statement), separated by calm content. On small sites, choose one main signature.
3
Motion lives in the background. Text stays still once it is read. Energy comes from slow ambient layers, image depth and well-made reveals, not from moving headings.
4
Nothing jumps. Animated components reserve their space. Swapping a caption, card or counter must never move the rest of the page.
5
Everything visible, everything loaded. No content depends on a reveal firing. No image is left unloaded because an effect hid it.
6
Every control goes somewhere. No dead links and no "page not found" from navigation. Features that need a server explain themselves in previews.
7
Less text, better text. Lead with what the reader needs. Scanned lists get icon + name + one line. Long passages get "Read more".
8
Accessible by construction. Semantic HTML first; keyboard and screen-reader parity; a designed reduced-motion version of every scene.
9
Editors are users too. Every visual option is a plain choice in the editor, with drafts, live preview, roles and version history.
10
Prove it, then show it. Automated tests, accessibility scans, overflow checks at every width, and link and image crawls before anything is shared. Report results honestly, failures included.

05 / Discovery, facts and content

Start from what is true

Inputs to request before designing

BrandOfficial logo files (SVG), colour values, typefaces and licences, existing guidelines.
FactsEvery claim the site may make, with its source and owner: names, numbers, prices, dates, results, addresses, contacts.
StructureAudiences and their top tasks; the information architecture (pages, parents, navigation labels); legacy URLs to redirect.
MediaReal photographs with release status and alt-text context; video if any; documents (PDFs).
OperationsWho edits what (roles); where forms should go (email, CRM webhook); analytics and consent requirements; hosting constraints.
DirectionReference sites and what the client likes in each; any visual "don'ts"; the devices and viewers they will review on (for example an iPad inside an app).

Facts register

Rule Keep a sources document listing every fact, where it came from, its owner and its status (approved, awaiting confirmation). Content awaiting confirmation is visibly labelled on the page. Results and figures carry a year label.

Writing for the site

  • Headings describe the content ("How to apply", not "Your journey begins"). Link text makes sense on its own.
  • Lead with the reader's need; short paragraphs; scanned lists are icon + name + one line; long passages get "Read more".
  • Dates and times in one human format ("Saturday 14 November 2026", "9:00am – 11:00am").
  • Alternative text describes what is happening and never names private individuals or children.
  • No personal data of minors or clients in content.

Questions to ask, and when not to

Ask when the answer changes what gets built (a missing fact, a brand rule, a conflict between instructions). Don't ask for things with a sensible default; state the default and proceed. When the owner says "your call", choose, explain briefly and keep the choice reversible in the editor.

06 / Visual system

Tokens by role, filled from the brand

Define tokens once and derive everything from them. Colours are defined by role; the client's brand fills the roles. Take values from the official logo file, not from screenshots.

Ink / primary
Headings, primary buttons, dark bands.
Accent
Eyebrows, focus ring, progress, links.
Highlight
Banners, underlines, focus on dark.
Secondary accents
Category cues, always with a text label.
Text / muted
Body and secondary text.
Tint
Alternate bands; avoid default cream.

Rule Body text at least 4.5:1, large text at least 3:1, including text over photographs. Muted text on dark bands stays at least 4.5:1, so check it as you dim. Never convey meaning by colour alone. Light accents (yellow, lime) are for graphics or carry dark text.

Originality

Use the client's own images, words and proportions. Extract relationships from references (stable labels against moving imagery, compressed text against open space, objects in their environment) rather than copying branded layouts, fonts or code.

07 / Page architecture

Explain, show, prove, act

Home page flow

  1. Promise + spatial hero. One sentence of outcome, two actions, the spiral gallery of real photographs, and a down-arrow scroll cue. About one viewport tall.
  2. Fact strip. Three or four verified facts.
  3. Progression chapter. The one sideways chapter: a real sequence (stages, product family, process).
  4. Purposeful showcases. A feature mosaic of three to five areas, each linking to its page.
  5. Lit statement. Two to four words that define the brand.
  6. Evidence. Stories, results, testimonials, process.
  7. Direct action. Visit, enquire, buy or contact, with addresses.

Interior page template

Hero (page, compact or category variant) → introduction → two to five content sections from the block library → related links → one call-to-action band. Breadcrumbs below the top level. Each audience reaches its top task within one click of the home page.

Block library (default set)

OpenersHero (home with spatial gallery, page with photo, category with label and colour, compact); Fact strip; Notice.
NarrativeText (aside, narrow or statement; becomes a sticky letter with a signature and portrait); Image and text; Feature mosaic; Lit statement; Word band.
ListsTerms (grid with descriptions, or spiral of icon + term + tagline); Link cards (grid or sideways row); Numbered steps (list or sideways row); Grouped lists; Table.
Media and peopleGallery with accessible viewer; People; Documents and resources.
DynamicLatest stories; Upcoming events (auto-hide when past); FAQ list (deep links); Locations with consent-gated maps; Pricing or admissions information from one source.
ActionEnquiry form; Call-to-action band; Reusable section (edited once, placed many times).

Site-wide essentials

Sticky header with click-to-open menus, a mobile menu dialog and search; a footer with contacts and policies; a sticky mobile primary action; a cookie banner with Accept, Reject and Customise; a search results page that works without JavaScript; a helpful 404; a sitemap, robots file, metadata and structured data; redirects from legacy URLs.

08 / Motion system

Three levels, one owner, calm by default

Level 1 is feedback (150–300ms). Level 2 is reveals and ambient motion (450–900ms, or tied to scroll position). Level 3 is the signature scenes: at most one per page. One frame-throttled scroll listener owns every scroll-driven effect. Native scrolling only: no smooth-scroll libraries and no wheel capture.

09 / Layout stability

Nothing jumps, nothing is lost

  • Rule Variable text in animated components sits in fixed slots (height, line clamp, fixed rows). Cycling every state must not move the next section.
  • Rule Images declare width and height and sit in aspect-ratio frames, with a focal point for crops. Media frames are never empty.
  • Rule Pinned scenes compute their length from measured overflow, re-measure on resize, fonts and images, and never pin when there is nothing to move.
  • Rule No horizontal page scroll at any width: clip decorative overflow on main; only tables and code scroll inside their own boxes.
  • Rule Server and browser render identical markup (no hydration mismatch). Components that read the URL also accept static-file addresses (/page.html).
  • Rule The first hero never animates in, and its main image is preloaded (fast largest paint).
10 / The content editor

Editors are users too

  • Block-based pages: add, reorder (drag), duplicate and remove sections; every visual option (spiral or grid, sideways row or grid, letter or plain text) is a labelled choice.
  • Drafts and publishing: autosave drafts; an explicit Publish; version history with restore; expiry dates for banners and events.
  • Live preview: the real page beside the form at phone, tablet and desktop sizes; drafts visible only to signed-in staff.
  • Roles: Contributor (drafts only), Editor (publish, menus), Specialist (for example admissions or sales: enquiries, events, prices), Administrator (everything, staff). The last administrator cannot be demoted.
  • Media library: alt text, approval status, release reference, focal point, automatic web sizes.
  • Shared settings: edited once and reused (contacts, locations, prices, menus, announcement).
  • Enquiries: created only by the site's forms; a status workflow; never readable through the public API.
  • Security: no public sign-up; lockout after 5 failures for 15 minutes; 8-hour sessions; optional single sign-on or network restriction for /admin.
  • Hand-over: a plain-English editor guide, a visual tour of real screens, and a "who approves what" table.

12 / Accessibility and reduced motion

Same content, every way in

  • Honour prefers-reduced-motion in CSS and JavaScript, live: no pinning, parallax, spiral turning, drifting labels or bands. Everything stays in normal flow.
  • Buttons for actions, links for navigation; 44×44px targets; a visible 3px focus ring (a highlight colour on dark bands).
  • Signature scenes keep a semantic list; galleries are keyboard reachable; skip links pass every pinned section; scrollable regions are focusable.
  • Decorative duplicates (rolling text, background labels, ornaments) are hidden from assistive technology and drawn as CSS-generated content where scanners would read them as text.
  • Dialogs: native modal, inert background, Escape closes, focus restored. Live regions for changing captions and form status.
  • Forms: real labels, validation on blur, an error summary, answers kept on error, spam controls without CAPTCHAs, consent-gated analytics and maps.
  • Zero serious or critical axe violations on representative pages after reveals settle.
13 / Performance, security, hosting and previews

Fast first, then rich

  • Responsive WebP sizes (about 400/800/1400/2200) and a 1200×630 share image; sizes per component; preload only the first hero image.
  • Lazy-load below the fold, except inside moving or pinned scenes (load eagerly there).
  • Animate transform and opacity only; requestAnimationFrame loops stop when settled; one scroll owner.
  • Ship only the icons used; share one small validation schema between browser and server.
  • Cache published content and invalidate it on publish; drafts bypass the cache.
  • Security headers: a content security policy listing only the third parties actually used (consent-gated); frame-ancestors 'self'; force https and HSTS only when served over https; remove framework banners; validate and rate-limit every form and API.
  • Targets: Lighthouse accessibility, best practices and SEO 100; performance at least 85 on mobile for key pages.

Hosting

A Node host, a PostgreSQL database, persistent or S3-type file storage, https, environment variables for secrets, a migration step on every deploy, backups, and staging before production. Document every setting in the README.

Static previews for review

When a build is shared as plain files (review links, artifact viewers): map server routes to files; build search from an exported index; make server-only features explain themselves; open every page at the top; retry dropped images; keep structured data byte-identical to avoid hydration mismatches; then crawl every link and image in the copy before sharing it.

14 / Implementation contract

Build it this way

  • Semantic, server-rendered HTML first; progressive enhancement; content visible without JavaScript.
  • One source of truth per scene (progress, selected item); the renderer is separate from the data.
  • Tokens in one file; one component per block (schema + renderer); migrations for every schema change.
  • Default stack (proven): Next.js with an embedded headless CMS (Payload), PostgreSQL, CSS modules, Playwright with axe, and Vitest. Any equivalent stack must meet the same contract.

15 / Process

From brief to launch

PhaseOutput
1. AnalyseRead every input; list facts, gaps and conflicts; ask only what changes the build.

Review etiquette. When feedback is short ("too much animation"), find the specific cause, remove it and replace it with a calmer alternative that keeps the intent. Don't just delete. When the owner reports something you can't reproduce (a white page on their device), remove the most likely causes, say plainly what couldn't be verified, and ask them to re-check.
