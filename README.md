# The International School @ ParkCity — website and CMS

A public website for The International School @ ParkCity (ISP), Kuala Lumpur, with a built-in content management system so school staff can maintain every page without touching code.

- **Public site:** Next.js 16 (App Router, React 19, TypeScript), server-rendered, cached and invalidated on publish.
- **Editor / CMS:** Payload CMS 3, running inside the same Next.js app at `/admin`.
- **Database:** PostgreSQL (schema managed by Payload migrations).
- **Media:** Local disk in development; any S3-compatible bucket in production.

The editor and the website share one content model: every page is a list of sections (“blocks”) that staff add, edit, reorder by drag-and-drop, preview live and publish.

> **Status: review build.** All copy and photographs come from the school’s own website (isp.edu.my, October 2026) and the research briefs. Items that need school sign-off before launch are listed in [`docs/CONTENT-SOURCES.md`](docs/CONTENT-SOURCES.md) and flagged on the relevant pages.

## Quick start

Requirements: **Node.js 20.9+** (22 recommended), **PostgreSQL 14+** (16 recommended).

```bash
# 1. Install dependencies
npm install

# 2. Start Postgres (or use your own and adjust DATABASE_URL)
docker compose up -d

# 3. Configure
cp .env.example .env
#    then set PAYLOAD_SECRET to a long random string:
#    openssl rand -hex 32

# 4. Load the ISP content (pages, stages, FAQs, events, stories, menus, images)
npm run seed
#    Images are downloaded from isp.edu.my on first run and cached in .seed-cache/.
#    The first administrator is created from SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD.

# 5. Run
npm run dev
```

- Website: <http://localhost:3000>
- Editor: <http://localhost:3000/admin> (sign in with the seed administrator, then change the password)

In development the database schema is pushed automatically from the config. To replace all website content with the seed again: `npm run seed -- --reset` (users and enquiries are kept), then restart `npm run dev` so cached pages are rebuilt.

## Architecture

```
src/
  app/
    (frontend)/        Public website routes: layout, [[...slug]] CMS pages, stories, search, 404, preview
    (payload)/         Payload admin UI and REST API (generated by Payload)
    sitemap.ts         Sitemap from published pages and stories
    robots.ts
  blocks/              One folder per section type: config.ts (CMS schema) + Component.tsx (renderer)
    RenderBlocks.tsx   Maps a page's sections to components
  collections/         Pages, Stories, Events, Programmes (learning stages), FAQs, Media, Users,
                       Enquiries, ReusableSections
  globals/             School details, Main menu, Footer, Admissions information
  access/              Roles and access-control functions
  fields/              Shared field definitions (links, slugs, SEO)
  hooks/               Cache revalidation on publish
  components/          Layout (header, menus, footer, search), consent, motion, UI primitives
  lib/                 Data queries, search, enquiry workflow, SEO, rate limiting, redirects
  endpoints/           Custom API endpoint (site search)
  admin/               Editor branding and dashboard guide
  migrations/          Database migrations
  seed/                Seed content (verified ISP copy) and image register
  styles/              Design tokens and base styles
tests/
  unit/                Validation, consent, utilities
  e2e/                 Navigation, search, forms, consent, accessibility, motion, CMS roles
```

Key decisions (details in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)):

- **Payload CMS** rather than a hand-built admin: proven authentication (lockout, sessions), role-based access, drafts and versions, live preview, block-based drag-and-drop editing, media processing and migrations, all self-hosted with the school’s data in its own database.
- **One content model:** the editor edits exactly what the public site renders. Reusable sections let a block be edited once and used on many pages.
- **Caching:** published content is cached and invalidated automatically when an editor publishes; drafts are only visible to signed-in staff in preview.
- **Forms:** a server action validates (shared schema), rate-limits, stores the enquiry in the CMS, then optionally emails staff and forwards to a webhook. Visitors see success only after the enquiry is stored.
- **Motion:** native scrolling with a single shared scroll listener, CSS transitions and transforms; no smooth-scroll hijacking. Everything has a reduced-motion and small-screen fallback.

## Configuration

All configuration is via environment variables; see [`.env.example`](.env.example) for the full list with comments. Never commit `.env`.

| Variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Yes | Postgres connection string |
| `PAYLOAD_SECRET` | Yes | Signs authentication tokens (long random string) |
| `NEXT_PUBLIC_SERVER_URL` | Yes | Public origin, e.g. `https://www.isp.edu.my`; used for canonical URLs, sitemap, CSRF and CORS |
| `SMTP_*`, `EMAIL_FROM_*` | Optional | Outgoing email (enquiry notifications, password resets) |
| `ENQUIRY_NOTIFY_TO` | Optional | Inbox for new-enquiry notifications |
| `ENQUIRY_FALLBACK_EMAIL` | Optional | Address shown if an enquiry cannot be stored |
| `ENQUIRY_WEBHOOK_URL`, `ENQUIRY_WEBHOOK_TOKEN` | Optional | Forward each enquiry as JSON to a CRM or admissions platform |
| `S3_*` | Optional | S3-compatible media storage |
| `NEXT_PUBLIC_GA_MEASUREMENT_ID` | Optional | Google Analytics 4, loaded only after a visitor accepts analytics cookies |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` | Seeding only | First administrator account |
| `PAYLOAD_DB_PUSH` | Optional | `false` disables development schema push |

## Deployment

The app is a standard Next.js Node server; it runs on any Node host (a VM or container, Render, Railway, Fly.io, AWS, Azure, etc.). Serverless platforms also work if media goes to S3 and the database accepts pooled connections.

1. **Provision** a PostgreSQL database and (recommended) an S3-compatible bucket for media.
2. **Set environment variables** (see above). Use HTTPS; in production, auth cookies are `Secure` and HSTS is sent.
3. **Build:** `npm ci && npm run build`. (The build does not need database access.)
4. **Migrate:** `npm run migrate` against the production database. The app also runs pending migrations on start (`prodMigrations`).
5. **Seed once** (optional, for a new database): `PAYLOAD_DB_PUSH=false npm run seed`, then restart the server.
6. **Start:** `npm start` behind a reverse proxy that sets `X-Real-IP` (used for rate limiting).
7. **Point the domain** and add the legacy redirects (built in, see `src/lib/redirects.mjs`) to the go-live checklist.

Notes:

- **After changing collections or blocks:** run `npm run migrate:create <name>`, commit the migration, and deploy.
- **Multiple instances:** the in-memory rate limiter is per instance; replace `src/lib/rate-limit.ts` with a shared store (e.g. Redis) behind the same function.
- **Backups:** back up the Postgres database and the media bucket on a schedule.
- **Uploads on local disk** (`./media`) are fine for a single server; use S3 for anything else.

## Integrations that need real credentials

| Integration | Status in this build | What is needed |
| --- | --- | --- |
| Email (SMTP) | Implemented, off until configured | SMTP host and credentials; a verified sending domain (SPF/DKIM) |
| Enquiry webhook (CRM / admissions platform) | Implemented, off until configured | Destination URL and token; JSON contract in `src/lib/enquiry/deliver.ts` |
| Media storage (S3-compatible) | Implemented, off until configured | Bucket, region/endpoint and access keys |
| Google Analytics 4 | Implemented, consent-gated, off until configured | Measurement ID; privacy notice updated by the school |
| Google Maps embeds | Implemented, consent-gated | None (uses public embed URLs) |
| Online application | Linked, not integrated | Final provider behind `bit.ly/ISPStudentapplication` must be confirmed by Admissions |
| Event booking | Linked | Admissions to confirm the booking URL for the 14 Nov 2026 open morning |
| Parent portal, SchoolsBuddy, calendar | Linked to the school’s existing systems | No login integration by design |

Nothing in the public site simulates a successful submission: if storage fails the visitor sees an error and an alternative email address.

## Known limitations

- **School approval required** for copy, photographs (student releases), results presentation, safeguarding contacts and legal pages before launch; see [`docs/CONTENT-SOURCES.md`](docs/CONTENT-SOURCES.md). Pages carrying a “Draft for school review” or “Awaiting school verification” notice should be resolved first.
- **Fee amounts** are not reproduced; the site links to the school’s official 2026/27 schedule. Finance can add an approved fee table in *Admissions information*.
- **Lighthouse performance** varies between runs (82–96) under simulated throttling; the main remaining cost is CSS and hydration on the home page. Real-user metrics should be measured after launch.
- **Live preview** refreshes on autosave; this was verified for display, not exhaustively for every block type.
- **Physical-device testing** (iOS Safari, Android Chrome) and a screen-reader session have not been done; emulated mobile and automated accessibility checks were.
- **Rate limiting** is per server instance (see Deployment).
- **Announcement expiry** is checked when a page is rendered; with caching, an expired banner can remain for up to an hour unless content is republished.
- **Scheduled publishing** is not enabled (it requires a background job runner).
